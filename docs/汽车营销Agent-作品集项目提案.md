# 汽车销售跟进与试驾邀约 Agent：作品集项目提案

日期：2026-11-19

状态：基于招聘 JD 和可接触一线销售顾问这一条件形成的方案草案。尚未完成访谈、产品开发或效果验证。本文的业务痛点是待验证假设，数据规模与排期是建议，不代表已有结果。

## 1. JD 实际考察的能力

截图中的岗位负责营销 Agent 的需求定义、设计、推广和持续迭代，强调融入一线工作流、任务编排、知识与工具调用、异常兜底、指标与评测。作品集应展示一个完整业务任务及其验证过程。

| JD 要求 | 作品集需要提供的证据 | 本项目对应设计 |
| --- | --- | --- |
| 深入一线，识别关键任务与障碍 | 访谈记录、现有流程、问题优先级及选择依据 | 销售顾问如何挑选待跟进客户、整理客户需求、准备试驾邀约 |
| 将专家经验转成复用能力 | 经验规则、适用条件、例外和版本记录 | 跟进优先级、需求信息清单、邀约时机与异议处理规则 |
| Agent 编排、知识与工具调用 | 实际运行的工具记录、来源引用、任务状态变化 | 查询客户记录、车型资料、活动规则、试驾档期，确认后创建待办 |
| 结果呈现、异常兜底和信任 | 用户能判断与修改结果；失败可恢复 | 区分事实和推断、标注缺失信息、显示失败步骤与重试入口 |
| 核心指标、Bad Case、实验和迭代 | 基线、评测集、失败分类、版本前后对比 | 人工流程与 Agent 辅助流程的耗时及可用性对比 |
| 推广与跨团队推进 | 试点计划、埋点、验收标准、实际用户反馈 | 从少量销售顾问试用开始，记录使用障碍与采用情况 |

个人作品集能证明问题定义、方案设计和验证能力；不能代替真实跨团队交付经历。涉及协作与业务收益时，应准确区分实际完成和未来方案。

## 2. 推荐项目与范围取舍

项目名：DriveFollow — 汽车销售跟进与试驾邀约 Agent。

一句话定位：帮助汽车销售顾问基于客户历史、车型知识与门店规则，形成今日跟进计划、准备有依据的试驾邀约，并记录结果与下一步行动。

主要用户是一线销售顾问。店长可作为策略与质量的评审者，首版不扩展成完整管理平台。

汽车销售通常包含线索分配、联系、需求确认、试驾邀约、到店、报价、下定、交付等阶段。本项目聚焦“已有线索的跟进准备—试驾邀约—结果记录”，避免把所有环节同时纳入首版。

| 方向 | 优点 | 代价与局限 | 结论 |
| --- | --- | --- | --- |
| 车型知识问答助手 | 容易制作和演示 | 对任务编排、运营策略和业务闭环的证明有限 | 作为项目内的一项能力 |
| 销售跟进与试驾邀约 Agent | 能覆盖 JD 的核心要求；有销售顾问可访谈验证 | 需要梳理实际规则和评测标准 | 推荐作为唯一主项目 |
| 自动触达及完整 CRM 平台 | 接近完整业务系统 | 真实渠道、系统权限和业务接入依赖较多，首版范围过大 | 后续有试点条件时再评估 |

## 3. 先验证的三个问题

以下均为假设，不应写成访谈结论：

1. 销售顾问是否需要花较多时间在多个记录中寻找客户背景？
2. 跟进优先级和邀约时机是否过度依赖个人记忆，容易产生遗漏？
3. 查找车型、金融方案或活动信息，以及把沟通结果整理成后续待办，是否存在明显摩擦？

若顾问已有工具很好地解决某个问题，应删减对应功能，把精力集中在仍未解决的高频任务上。

## 4. 可演示的一次完整任务

销售顾问输入：“帮我安排今天优先跟进的客户，并给出试驾邀约建议。”

系统执行：

1. 读取分配给该顾问的客户、最近跟进记录和已有任务，检查数据是否足够。
2. 依据经访谈确认的规则排序，展示影响排序的事实；排序表示工作优先级，不冒充成交概率预测。
3. 为选中的客户提取明确需求，查询版本和有效期可追溯的车型、活动及门店信息。
4. 输出客户摘要、推荐下一步、邀约草稿、引用来源、需要补问的信息。
5. 顾问修改或确认后创建跟进任务。仅在客户时间意向与可用档期均确认时创建模拟预约。
6. 顾问记录联系结果，如已预约、暂缓、时间不合适、未接通，系统更新下一步任务。
7. 保存采用、修改、驳回及其原因，供后续评测和迭代使用。

演示客户示例（虚构）：客户关注家庭出行、后排空间和儿童座椅安装，跟进记录中明确表示周末有时间，但尚未确认具体档期。Agent 引用客户记录与车型资料，建议提供一次围绕家庭乘坐体验的试驾，并先确认时间。它不会把“周末有空”直接写成“预约成功”。

## 5. 首版四个页面

### 今日跟进工作台

显示待办、待跟进客户、优先级依据、数据缺口及任务状态。用户从日常工作入口直接发起任务。

### 客户行动卡

同屏展示客户事实、来源、推荐动作、邀约草稿和顾问反馈。区分记录明确说明的事实与模型提出的推断。支持修改、采用、驳回和补充信息。

### 跟进与预约记录

支持确认后创建待办、查询模拟档期、创建模拟预约、记录沟通结果和安排下次跟进。对重复提交做去重，避免生成重复任务。

### 质量与迭代记录

展示任务完成情况、处理时间、结果采用情况、工具失败、Bad Case 和规则版本。首版可以是轻量报告页，不需要建设复杂分析平台。

## 6. 技术上要真正跑通的部分

建议采用一个可控工作流和必要的工具调用。客户状态、规则过滤、预约档期与写入校验由程序处理；模型负责对话记录提取、信息组织及个性化草稿。由此明确模型与确定性逻辑的职责。

建议工具：

- 查询客户和跟进历史。
- 检索车型与活动资料，返回来源、版本与有效期。
- 查询门店试驾档期。
- 创建跟进任务、保存结果、创建模拟预约。

开发可用一个 Web 应用、轻量数据库和模型 API 完成。优先使用结构化车型参数与活动规则；存在长文本资料时再加入检索。技术栈和模型在开发设计阶段选择。

首版使用虚构或经允许脱敏的数据，CRM、消息触达和预约系统通过本地模拟工具演示，并在界面标明模拟环境。模型生成与工具读写应实际执行，避免全部依赖预录结果。

建议准备 50—100 条覆盖不同状态的演示线索、少量车型与门店活动资料。数量服务于演示与评测，不用于声称拥有真实业务规模。

## 7. 必须演示的异常情况

| 情况 | 产品行为 |
| --- | --- |
| 需求或联系方式状态不完整 | 显示缺失项，提出补问建议，不补造事实 |
| 车型或活动资料缺失、过期、冲突 | 标明问题，暂不输出确定性配置或优惠承诺 |
| 客户明确拒绝继续联系 | 根据经确认的业务规则排除触达任务 |
| 客户记录存在待处理投诉 | 转为投诉跟进建议，避免直接进入邀约流程 |
| 查询工具失败 | 保留已完成步骤，明确失败位置，允许重试 |
| 预约档期不可用或提交失败 | 显示待确认或失败，提供替代档期，不报成功 |
| 重复点击确认 | 复用已有结果或提示已创建，避免重复写入 |

## 8. 访谈安排

建议先访谈 3—5 位销售顾问；这是发现问题的起点，不代表样本具有统计代表性。条件允许时，请店长或资深顾问补充验证规则。

每次约 30 分钟，围绕近期具体案例，避免只问“愿不愿意使用 AI”。

1. 请用最近一个工作日，说明你如何决定先联系哪些客户。
2. 选一条已脱敏线索，演示从接手到发起试驾邀约需要查看什么、在哪些工具操作。
3. 哪一步最费时间？哪一步最容易漏掉？现有工具已经解决了哪些问题？
4. 最近一次客户愿意试驾与最近一次邀约失败，分别发生了什么？
5. 判断值得跟进和暂不该联系时，具体依据是什么？哪些情况是例外？
6. 配置、报价、优惠和金融信息分别从哪里核实？更新后如何获知？
7. 看一张示例行动卡：哪些内容能直接用，哪些需要修改，哪些错误不能接受？
8. 完成联系后如何记录结果？是否会遗漏下次行动？

访谈产物：现状流程图、逐条可追溯的发现、按频率和影响排序的问题、可执行的规则与例外。不要把个人猜测或模型生成的回答当成用户证据。

## 9. 验证与指标

### 无真实系统接入时也能开展的验证

先制作 30—50 个场景，覆盖正常任务和关键异常。划分开发用案例与未参与调优的留出案例。评审标准由真实销售顾问参与制定；如存在多种合理行动，应允许多个合格答案。

比较人工使用同一份资料完成任务与 Agent 辅助完成任务的表现。使用难度匹配的不同案例，并平衡任务顺序，减少重复见到同一案例带来的学习影响。有余力再加入普通聊天模型作为第三组。

| 指标 | 定义和使用方法 |
| --- | --- |
| 任务可用率 | 经顾问审阅，事实、规则和必要步骤均合格的结果数 / 被评审任务数；报告实际样本量 |
| 准备耗时 | 从打开任务到确认可执行方案的总时间，包含顾问核查和修改时间 |
| 采用与修改情况 | 分别记录直接采用、修改后采用、驳回及原因，不只统计点击采用 |
| 关键事实错误 | 单独统计车型、优惠、客户需求和预约状态错误，避免平均分掩盖严重错误 |
| 工具执行成功率 | 按读写工具记录成功、失败、重试和重复写入，区分模型输出正确与动作真正执行 |
| 成本和响应时长 | 按任务记录模型费用与耗时，给出样本量及实际观测值 |

展示一次实质迭代，例如开发案例中发现活动过期处理错误，增加有效期校验，再在留出案例检验。用真实评测结果填写前后对比，不预设提升数字。

### 获得真实试点后再验证

- 使用渗透：有符合条件任务的顾问中，实际使用 Agent 的人数及重复使用情况。
- 试驾预约率：固定观察窗口内形成有效预约的去重线索数 / 纳入同一口径的合格线索数。
- 到店率：固定观察窗口内实际到店的客户数 / 对应有效预约客户数。
- 同时观察联系频次、拒绝联系和投诉情况。

上线前固定观察窗口、去重口径、线索来源和分组方式。小样本试用报告描述性结果，不声称统计显著或因果提升。没有真实试点时，作品集只写离线评测与用户任务测试结果。

## 10. 最终作品集交付

1. 问题研究：访谈记录、当前工作流、证据与问题优先级。
2. 产品方案：目标用户、MVP 边界、关键决策、业务规则和验收标准。
3. 可运行 Demo：一条完整正常流程和至少两条异常流程。
4. Agent 设计说明：知识来源、工具契约、任务状态、人工确认与恢复方式。
5. 评测报告：基线、样本、评审口径、真实结果、Bad Case 和一次迭代。
6. 3—5 分钟演示视频：从顾问发起任务到结果落库，说明每个关键设计解决的问题。

简历表述模板（仅在实际完成后使用，并填入实测数据）：

> 独立设计并实现面向汽车销售顾问的线索跟进与试驾邀约 Agent；通过 X 位顾问访谈提炼跟进规则，搭建客户信息查询、车型知识引用、模拟预约及任务记录流程，构建 Y 个评测案例，并基于错误分析完成一轮迭代。在 Z 次用户任务测试中，记录到准备耗时由 A 变为 B，结果可用率为 C。

## 11. 建议推进节奏

以下是全职或高投入情况下的初步估计，实际取决于访谈时间、开发基础和模型接入条件：

- 第 1 阶段，约 2—4 天：访谈、复现现有任务、确定首要痛点和评审标准。
- 第 2 阶段，约 1—2 天：完成关键页面草图、数据结构、工具契约和验收案例。
- 第 3 阶段，约 5—8 天：实现完整主流程、必要异常处理和运行记录。
- 第 4 阶段，约 3—5 天：顾问任务测试、留出集评测、修复主要问题、整理作品集。

项目的第一里程碑是：一位销售顾问能对照真实工作判断，这条端到端流程解决了一个具体问题。随后才决定是否扩展功能。
